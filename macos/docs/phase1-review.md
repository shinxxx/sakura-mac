# 阶段 1 验收（第 23 步）

**结论**：阶段 1（核心库移植，第 12～23 步）完成。macOS 上 Mac 核心库的单元测试 956 个全部通过（GitHub Actions 的 macOS 26 arm64，`arm64;x86_64` 通用二进制），另有 3 个测试是原版本身标成 `DISABLED_` 的。Windows 版按 2026-11-09 项目负责人的决定不再构建，这一步没有用 Windows 构建确认，只按代码规则确认（见下文）。重新估算后，剩下的阶段 2～4 大约还要 **3 到 5 个月**，比计划开始时估计的剩余时间（约 7 到 11 个月）短。

## 3. 对 Windows 版的影响

计划的验收标准里有“Windows 构建不受影响”。但 2026-11-09 项目负责人决定 Mac 版只关注 Mac、不维护 Windows 版，`macos` 分支从那天起不再自动跑 Windows 的完整构建（第 11 步）；2026-11-10 又确认不需要手动跑一次。所以这一步**没有用 Windows 构建确认**，只确认了以下几点：

- 原版代码的改动遵守同一个规则：Mac 专用的代码用 `#if defined(_WIN32)` 隔开，或者改成在 Windows 上结果不变的写法。各步骤改了哪些原版文件，都列在对应的说明文档里（`phase1-*.md`）。
- 规模：与上游 `4fe60275c` 相比，`sakura_core` 有 422 个文件变化（新增 11241 行、删除 9372 行），大部分是第 14 步的字符类型替换（`L"…"` → `LTEXT("…")` 等）。第 14 步当时在 Windows 上构建并通过了测试。上游合并之后（第 19～22 步），`sakura_core` 有 36 个文件变化（新增 907 行、删除 26 行），其中新加了 110 处 `_WIN32` 的条件编译。
- 第 22 步的核心库接口没有修改原版文件。
- Windows 上仍在运行的检查（字符类型的测试 `wchar16-test-windows`、代码页表的导出 `codepage-dump-windows`）都通过。它们不编译 `sakura_core`。

以后如果要回馈上游（第 53 步前联系上游时决定），需要先恢复 Windows 构建确认一次：去掉各工作流里 `branches-ignore` 的两行即可。

## 4. 重新估算后续工期

### 实际进度

| 阶段 | 计划的估算 | 实际 |
| --- | --- | --- |
| 阶段 0：立项与准备（第 1～11 步） | 约 2 周 | 2026-11-08～11-09，约 2 天（其中 2 步按你的决定推迟到后面） |
| 阶段 1：核心库移植（第 12～23 步） | 约 1 到 2 个月 | 2026-11-09～11-11，约 3 天 |

计划开始时的估算是按“一个人全职开发”算的。实际上代码由我来写，你负责决定和审阅，阶段 0、1 合计用了约 4 天。

### 为什么后面不会一样快

阶段 1 的工作几乎都能用自动测试验收：编码、查找、设置文件，都能在 CI 上和原版的结果逐字节比较。后面的阶段不一样：

1. **需要在真的 Mac 上看和用**：输入法（第 25 步）、绘制（第 28 步）、窗口和菜单（第 26、35 步）是否正常，CI 只能确认能编译、能启动，好不好用要你在 Mac 上实际操作。每个这样的步骤估计要来回 1 到 3 次。这部分的速度主要取决于你能拿出多少时间试用。
2. **界面要重写，不是移植**：对话框、设置页面约 5 万行 Windows 代码要用 AppKit 重新做，工作量比阶段 1 大得多。
3. **有外部等待**：Apple Developer Program 的注册（第 36 步前必须完成）、TestFlight 测试者的反馈（第 38 步）、App Store 审核（第 56、57 步，一般 1 到 3 天，被拒的话要再来一轮）。
4. **输入法风险最高**：第 25 步如果发现自绘视图接不好日文、中文输入法，可能要改方案，这是最大的不确定因素。
