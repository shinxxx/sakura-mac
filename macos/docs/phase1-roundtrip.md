# 阶段 1 第 18 步：编码往返测试

**结论**：87 个样本（内置编码 14 个、代码页 73 个）读入后再写出，字节与原文件完全一致；读入的文字也与独立生成的期望文本完全一致。Mac 核心库的全部 686 个测试通过。

## 做法

| 项目 | 内容 |
| --- | --- |
| 样本 | `macos/core/tests/data/roundtrip/`，每个样本有 `名前.bin`（编码后的文件）和 `名前.txt`（期望文本，UTF-8），清单是 `manifest.tsv` |
| 样本的生成 | `macos/tools/make_roundtrip_samples.py`。用 Python 自带的编码器生成，与 Sakura、Windows 是不同的实现，所以“读入结果等于期望文本”是独立的验证 |
| 文本 | 英文、ASCII 符号、西欧、中欧、俄文、希腊文、土耳其文、立陶宛文、希伯来文、阿拉伯文、泰文、日文（含半角假名）、简体中文、繁体中文、韩文、BMP 以外的字符（😀、𠮷）。每种编码只用 Python 能严格编码的行 |
| 换行符 | 每行轮流使用 CRLF、LF、CR，最后一行没有换行符 |
| 读入 | 与原版 `io/CFileLoad.cpp` 相同：`CodeToUnicode` 解码，开头的 U+FEFF 当作 BOM 去掉 |
| 写出 | 与原版 `env/CWriteManager.cpp` 相同：有 BOM 时在第一行前加 U+FEFF，每行（含换行符）分别 `UnicodeToCode` 后连接。样本也按这种逐行的方式生成，所以 ISO-2022 等有状态的编码每行重新指定字符集 |
| 测试 | `macos/core/tests/test-mac-roundtrip.cpp`，每个样本一个测试（`Samples/RoundTrip.LoadThenSaveIsByteIdentical/名前`） |

原版的 `CWriteManager` 依赖设置模块（共享内存），第 21 步之后才能编进 Mac 版，所以写出按它的做法直接调用同样的转换函数。读入从第 20 步起改为走真正的 `CFileLoad`（含分段读取），见[文档模型和语法类型](phase1-doc-types.md)。第 29 步“打开与保存”时，再用同一批样本在 App 里验证一次。

## Python 与 Windows 不同的地方

下面这些字符，Python 的映射与 Windows 不同（Windows 一侧以第 17 步在 Windows 上导出的转换表为准），样本里不用。

| 代码页 | 不用的文本 | 原因 |
| --- | --- | --- |
| 950 | 日文 | Windows 把 Big5 的日文假名区（C6A1〜C7FC）映射到私用区，Python 映射到假名 |
| 10006、10007、10010、10079、10082 | € | Windows 的 Mac 系代码页用旧版 Apple 映射，该位置是 ¤（U+00A4） |
| 20932 | 西欧、中欧、土耳其文、立陶宛文、希腊文 | Windows 20932 不支持 JIS X 0212（8F 开头的 3 字节），这些带重音的字母会变成“?” |
| 28597 | € | Windows 28597 没有 €（ISO-8859-7:2003 才加入） |
| UTF-7（5、65000） | ASCII 符号 | `!"#$%&` 等（RFC 2152 的 Set O）Windows 是直接写出还是用 base64 没有确认 |

另外，UTF-7 的 base64 段之后，Python 在下一个字符不是 base64 字符时省略结束符“-”，Windows 和原版 Sakura 总是写“-”。两种写法解码结果相同，样本按 Windows 的写法生成（脚本里自己编码，再用 Python 的解码器确认）。

## 重新生成样本

```sh
python3 macos/tools/make_roundtrip_samples.py --check   # 检查仓库里的样本与生成结果是否一致
python3 macos/tools/make_roundtrip_samples.py           # 重新生成
```

样本只在需要时（加文本、加编码）重新生成，生成后要在 Mac 上跑测试确认。`data/roundtrip/.gitattributes` 让 Git 不改动这些文件的换行符。
